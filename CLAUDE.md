# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`setono/sylius-gift-card-plugin` — a Sylius plugin adding gift card functionality. Version 1.x (branch `1.x`) is a full rewrite targeting Sylius 1.13 and up, PHP >= 8.1, Symfony ^6.4.

`composer.json` conflicts with `twig/twig >=3.29` on purpose, and the conflict stays while the plugin supports PHP 8.1. Twig 3.29 made `TemplateWrapper::unwrap()` require the environment, and `sylius/mailer-bundle` up to 2.2.0 calls it without one, so every email fails. The fixed mailer bundle (2.2.1) needs PHP 8.2, and Composer cannot tie the Twig conflict to the mailer bundle's version. Do not lift the conflict on its own. When PHP 8.1 is dropped, raise `require.php` to `>=8.2` and replace the Twig conflict with `"sylius/mailer-bundle": "<2.2.1"` in the same change. Then update the README's "Twig below 3.29" section, the CHANGELOG and UPGRADE-1.0.md, which explain it to users.

Key feature set: customers buy gift cards choosing the amount themselves (virtual = email delivery, physical = shipped + design chosen by the customer); redeeming a gift card creates a real Payment entity against the order, leaving the order total intact — a gift card settles a liability the shop already took money for, so it is a means of payment rather than a discount. No API layer.

## Commands

```bash
composer analyse           # PHPStan at max level (phpstan.neon)
composer check-style       # ECS check (ecs.php)
composer fix-style         # ECS auto-fix
composer rector            # Rector dry run (rector.php)
composer lint              # lint:container, lint:twig and lint:yaml through the test application (each is a script of its own too)
composer phpunit           # full PHPUnit suite
vendor/bin/phpunit --testsuite unit        # unit tests only (no database needed)
vendor/bin/phpunit --testsuite functional  # functional tests (require MySQL with the schema, see below)
(cd tests/Application && bin/console doctrine:database:create --env=test && bin/console doctrine:schema:create --env=test)  # once, before the first functional run
vendor/bin/phpunit tests/Unit/Path/To/SomeTest.php   # single test file
vendor/bin/phpunit --filter testMethodName           # single test method
vendor/bin/infection --threads=max --test-framework-options="--testsuite=unit"   # mutation testing, as CI runs it (needs pcov or Xdebug)
```

On PHP 8.4, add `--initial-tests-php-options="-d error_reporting=E_ALL&~E_DEPRECATED"` to the Infection command: PHP 8.4 reports api-platform 2.7's implicitly nullable parameters as deprecated, and Infection gives up when its initial test run writes anything to stderr.

CI runs `composer rector`, `composer lint:yaml`, `composer lint:twig` and `composer lint:container` as they are, so a change to what they check goes in `composer.json`.

## Test application

`tests/Application/` contains a full Sylius app used as the kernel for PHPUnit (bootstrap `tests/Application/config/bootstrap.php`) and for manual/browser verification. Run its console with `(cd tests/Application && bin/console ...)`. It needs a MySQL database (`DATABASE_URL` in `tests/Application/.env`) and built assets (`yarn install && yarn build` inside tests/Application). Admin credentials after fixtures: username `sylius`, password `sylius`.

**Always run the web server with `symfony serve`** (e.g. `(cd tests/Application && symfony serve -d --port=8080)`) — never `php -S` / `symfony php -S ... router.php`. `symfony serve` handles routing itself (no `router.php` needed) and serves from `public/` automatically.

`public/index.php` and `bin/console` leave deprecations out of PHP's own error reporting before they load Composer's autoloader, so no deprecation ends up in a page or in a command's output on any PHP version; Symfony still logs every one its error handler receives. Keep both. On PHP 8.4 the autoloader runs api-platform 2.7's `deprecation.php`, which loads interfaces PHP reports as deprecated while compiling them, before `Debug::enable()` has run, and a development php.ini printed those notices into the output: at the top of every console command's (#447), and at the top of a page whenever OPcache compiled those files afresh (after the server started, and after a few container rebuilds had filled OPcache's memory), which then failed with a 500 because its session could not start (#434). Under OPcache those notices never reach Symfony's handler anyway (php-src GH-17422). symfony/runtime, which Sylius-Standard uses, also runs the autoloader before it registers its error handler, so switching to it would not help.

**Assets: use Node 20** (`tests/Application/.nvmrc` pins it — run `nvm use` before `yarn install`/`yarn build`). The frontend uses `@sylius-ui/frontend` (Dart Sass); Node 22+ breaks the build. `package.json` also pins `jquery` via `resolutions` so the admin JS (`jquery.dirtyforms`) loads — without it the admin console throws `jQuery.dirtyForms is not a function` and JS-driven form submits fail.

## Testing conventions

- Unit tests live in `tests/Unit`, functional tests (KernelTestCase/WebTestCase booting the test app) in `tests/Functional`.
- Functional tests need the test database's schema, which they never build or change themselves: CI creates it with `doctrine:schema:create`, and locally it is created once (see Commands; after a mapping change, drop and create it again, or run `doctrine:schema:update --force --env=test`). Every test runs in a transaction that `dama/doctrine-test-bundle` (registered as a PHPUnit extension in `phpunit.xml.dist`) rolls back afterwards, so each starts from an empty database. A test that needs its writes really committed, because a second connection has to see them or wait on their locks, opts out the way `GiftCardRedemptionRaceTest` does: a plain connection (`StaticDriver::setKeepStaticConnections(false)` before the kernel boots), and the tables emptied in `tearDown()`.
- CI fails when the tests lose ground. The mutation job holds Infection to `minMsi` and `minCoveredMsi` in `infection.json.dist`, and Codecov holds the coverage report to the targets in `codecov.yml`: the project's coverage, and 80% of the lines a change adds or modifies. The minimums sit a little below what the suites reach and only ever go up: when your tests raise a score, raise its minimum in the same change, and never lower one to get a change through.
- Use a BDD-style naming convention for test methods (`it_does_something`) with the `@test` annotation or `test` prefix.
- Use Prophecy for mocking (phpspec/prophecy-phpunit), not PHPUnit mock objects.
- Form type tests extend `Symfony\Component\Form\Test\TypeTestCase`.
- Form types should bind to a `data_class` rather than produce an array — so the rules travel with the data instead of with the one form that happens to produce it, and consumers get a typed object instead of an array shape annotation. See `AdjustGiftCardBalanceCommand` / `AddGiftCardToOrderCommand`.
- Validation constraints are declared in XML under `src/Resources/config/validation/`, one file per class, never as PHP attributes — models and command objects alike. Host applications override plugin validation by pointing at these files, which only works if every constraint lives there.

## UI testing with Playwright

UI MUST be covered by **Playwright tests**, not just looked at once. Ad-hoc checking only ever exercises the page you happened to change, so regressions on every other page go unnoticed — a dropped option in the test app's `_details.html.twig` override left *every* non-simple product's admin edit page returning a 500, and manual verification of the gift card pages never touched it.

The suite lives in `tests/Playwright` and runs against `tests/Application` served in its **test** environment, on a database of its own:

```bash
cd tests/Application
export APP_ENV=test DATABASE_URL='mysql://root@127.0.0.1/setono_sylius_gift_card_e2e?serverVersion=5.7'
bin/console doctrine:database:create && bin/console doctrine:schema:create && bin/console sylius:fixtures:load -n
symfony serve -d --port=8080              # passes APP_ENV and DATABASE_URL on to the application
cd ../Playwright && yarn install && npx playwright install chromium
npx playwright test                       # whole suite
npx playwright test --project=admin       # admin specs only
npx playwright test --headed -g 'cart'    # watch a single test
```

The database is not the test environment's default (`setono_sylius_gift_card_test`): that one is the functional suite's, which expects it empty, and fixtures loaded into it break the functional tests. To reseed for a fresh run, `doctrine:database:drop --force` and the three commands again, with the same two variables exported. Restart the server (`symfony server:stop`, then serve again) whenever code or configuration changed since it started, as CI serves each job from a fresh one. Every container rebuild adds a new container's files to php-fpm's opcache, which one container and a run of the suite already nearly fill (128 MB by default). On a server that had outlived a few rebuilds, requests started failing at random mid-run: PHP 8.4 printed api-platform's implicitly nullable deprecation notices ahead of the page, and the native session then refused to start ("headers already sent"). To browse the app by hand in dev afterwards, stop the server (`symfony server:stop`) and serve it again from a shell without the two variables.

`PLAYWRIGHT_BASE_URL` overrides the default `https://127.0.0.1:8080`. CI splits the suite into three parallel jobs (`npx playwright test --shard=N/3`), each against an application and a freshly seeded database of its own, so a spec cannot count on another spec having run before it. CI runs without retries, so a spec has to pass at the first attempt: a test that legitimately needs longer than the 30 s default (a whole checkout walk, or a couple of dozen admin page loads) calls `test.slow()` with a comment saying why. How long a spec takes must not hang on what Sylius' fixtures pick at random, so the test application pins what it does: one enabled shipping method in each zone, so that every country the shop offers is shipped to and `support/checkout.js` goes on with the first country it tries (when all three methods drew the US zone, it submitted an address in every other country first, #468). The admin specs share a signed-in session created by `specs/auth.setup.js`; the shop specs run anonymously, and sign in with `signInAsAdministrator()` when a journey ends in the admin.

The test environment is what the suite needs: Sylius renders its `data-test-*` hooks only in an environment whose name starts with `test`, and the environment has no web debug toolbar, whose list of AJAX requests is a table of its own on every page (#427). Its sessions suit a real browser too: `ServedOrMockSessionStorageFactory` (`tests/Application/Session/`, wired in `config/services_test.yaml`) gives the functional tests Symfony's mock file storage, as PHPUnit needs, and the served application PHP's native session, whose locking keeps a page and the AJAX request it sends from undoing each other's session writes (with the mock storage, a flash added while another request of the same session was running was lost every time). So **specs address what they check through hooks, never through English text**: Sylius' (`[data-test-cart-grand-total]`, `[data-test-flash-messages]`, `[data-test-grid-table-body]`, `[data-test-show-product-in-shop-page]`, ...) and the plugin's. The one exception is Sylius' own admin labels, which the admin specs may still read: order and payment states, the labels of a show page's details table, and buttons such as *Filter* and *Delete*. The admin renders in the administrator's locale, not the shop's, and Sylius has hooks for few of them. A spec that needs a hook the plugin's templates lack adds it with `{{ sylius_test_html_attribute('name', value) }}`, never a raw `data-test-*` attribute, so a shop's prod environment renders none. Rows are read from the table they belong to, never a bare `table tbody tr`: a grid's through `GRID_ROWS` (`support/admin.js`, Sylius' `[data-test-grid-table-body] > tr`), a card's ledger through `[data-test-gift-card-transaction]`, and any other Sylius table as `table.ui.table`. Money is compared in minor units (`moneyInCents()`, the cart's `cartFigure()`, a checkout step's `checkoutFigure()`), whatever the locale's separators, and preferably figure against figure. Messages are only matched by their wording where the wording is what the spec is about (a translated validation message in the admin, say).

Specs must **discover their subjects** rather than hardcode ids, slugs, codes or locales, so they keep working against a freshly seeded database. `support/shop.js` takes the locale from the shop's first redirect (`shopLocale()`, `shopPath()`, `shopLocales()` adds the switcher's) and the gift card and ordinary products from the links on the home page (`giftCardProductPath()`, `ordinaryProductPath()`). The test application seeds two gift card products, `gift_card` with both delivery types and a virtual-only one. Both are the newest products, so the home page lists both, in either order, and `discoverProducts()` tells them apart by the gift card product page's delivery choice (`DELIVERY_CHOICE`): `giftCardProductPath()` is the one offering a choice of delivery types, `singleDeliveryTypeGiftCardProductPath()` the one without. The gift card product page prints no price, so `listedPrice()` reads the one the home page's box of the product shows. `support/fixtures.js` finds records through the admin grids: `productIdsByKind()` walks the whole products grid and tells gift card products from the others by the state of the product form's gift card checkbox (every product form has one), and `productShopPath()` reads a product's shop page off its edit page. The only codes known up front are the test application's seeded `E2E*` cards, which specs apply to carts but never spend; a spec that spends, changes or deletes a card issues its own with `issueGiftCard()`. Whatever else a spec creates or changes (a design, a product, a payment method's instructions, a product's flag) it removes or restores in a `finally`.

Wait for what a click leads to with `clickAndWaitForPage()`, `waitForURL()` or a web-first assertion, never `waitForLoadState('networkidle')`, which resolves early or late depending on what else the page loads.

Any new UI needs a spec here. Coverage today: admin gift cards index/show/edit (the grid's status column, filters, sorting and delete visibility; the show page's status and its order and design links; the redirect to the show page after a balance adjustment; the show page's ledger, with the admin who adjusted a balance and the order that issued a bought card), issuing (with the create form's design picker, its thumbnails narrowed to the chosen channel, and the delivery type), balance adjustments and deletion, designs index/edit (channels column, sorting by name) and their management, the setup warning, balance report, gift card and design preview PDFs, product edit for simple/configurable/gift card products and product scaffolding, and the shop gift card product page (the plugin's own page: what it leaves out of Sylius', the order of its parts wide and narrow, the delivery choice, the quantity, the amount starting at the listed price), locales, add-to-cart (also of a gift card product with a single delivery type, whose page has no delivery choice), buying a card, redemption, what the cards cover and what remains to pay on every checkout step up to placing the order (with a card covering the order in full and in part), checking out with a card that pays the order in full or in part, and a card going stale before the order is placed.

Sylius ships Semantic UI 2.5, and an icon name its stylesheet lacks (`palette`, say) renders as a blank without any error. So the specs check that every icon draws, with `support/icons.js`: on each plugin admin page as a whole (`admin/icons.spec.js`), and where an icon only shows in some state (the status labels, the setup warnings, the cart's remove button). A new page goes into `admin/icons.spec.js`.

Redemption does not change what the order costs — the gift card becomes a payment against it — so specs assert the "Remaining to pay" figure rather than expecting the order total to drop.

When a test app template overrides a Sylius one, diff it against the original in `vendor/sylius/sylius/.../Resources/views/` before trusting it; the override silently drifts as Sylius changes, and options dropped from a `form_row` call fail only at render time.

Use the Playwright MCP tools (configured in `.mcp.json`) while developing a change, but land the coverage as a spec.

## Architecture

Namespace `Setono\SyliusGiftCardPlugin\` maps to `src/`; tests are `Setono\SyliusGiftCardPlugin\Tests\` in `tests/`. Bundle class `src/SetonoSyliusGiftCardPlugin.php`; services are XML files under `src/Resources/config/services/` imported by `services.xml`. The DI extension prepends configuration for other bundles (winzou state machine, sylius_ui, sylius_grid, liip_imagine, sylius_mailer) as PHP arrays built in `prepend()` — host apps do not import plugin config manually. Register the bundle before SyliusGridBundle.

Routes live in `src/Resources/config/routes/` (`shop.yaml`, `admin.yaml`, `admin_ajax.yaml`), and applications import them through `routes.yaml`, or `routes_no_locale.yaml` when their shop URLs carry no locale (the name 0.11/0.12 shops already import). The two register the same routes except that `routes.yaml` puts the shop ones under `/{_locale}`, so a route file added to one goes in the other too; `tests/Functional/RoutesWithoutLocaleTest.php` fails when they drift.

Services are always injected by their **interface alias**, never by the class id. Symfony applies a decorator of an alias by re-pointing that alias only, so a service built with the class id silently skips the decorator an application registers on the interface (the README tells them to decorate the interface). Every service implementing a plugin interface gets an alias for it, and the winzou callbacks name the public interface alias rather than the class. `tests/Unit/DependencyInjection/InterfaceAliasWiringTest.php` fails when any of this drifts.

A service whose id is its class name leaves out `class`. Symfony's `ResolveClassPass` takes the class from an id that is a fully qualified class name, so writing it again is only a second copy to keep in step. `class` is written only where it differs from the id, as on a dotted id. `tests/Unit/DependencyInjection/ServiceClassFromIdTest.php` fails on a definition that repeats its id as its class.

State machine callbacks are registered twice, once as winzou callbacks in `prepend()` and once as Symfony Workflow subscribers in `src/EventSubscriber/Workflow/`, so the plugin works under either adapter. Keep the two in sync when changing them. **Every callback declares an explicit priority on both sides, with a one-line reason placing it relative to Sylius' own callbacks.** winzou runs callbacks in ascending priority order and Sylius' sit at -800..-100, so an unprioritised callback (0) silently runs after everything Sylius does — that is how `reconcile` came to run after an order had already been paid and its cards enabled. Symfony's dispatcher runs listeners descending, with Sylius' at 100..800, so a workflow subscriber's priority is the negated winzou priority. `tests/Unit/DependencyInjection/StateMachineCallbackParityTest.php` builds the config from `prepend()` and fails when the two sets drift (transition, collaborator method or priority).

Anything reacting to a Symfony event is an **event subscriber**, so the event name and priority live in `getSubscribedEvents()` next to the code rather than in a service tag. `kernel.event_listener` is only used where a subscriber is impossible — currently Sylius' own `ImagesUploadListener`, which we cannot add the interface to. Doctrine's `onFlush` listener is a Doctrine event, not a Symfony one, and stays a listener. Subscriber services are registered in `services/event_subscriber.xml` and listeners in `services/event_listener.xml`, except the Symfony Workflow subscribers, which stay in `services/workflow.xml` as the twins of the winzou callbacks.

The shop shows a gift card product on the plugin's own page, `shop/product/show.html.twig`, not Sylius' product page: the live preview of the card in the first column, and in the second the product's name and Sylius' add to cart form (its route, CSRF token and redirect, built and rendered by Sylius' partial cart route with the plugin's `_add_to_cart_form.html.twig`) holding the delivery choice (only for a product with more than one variant), amount, design, message and quantity. `GiftCardProductPageSubscriber` renders it on `sylius.product.show`, which Sylius' resource controller answers with the response a listener sets, for the `sylius_shop_product_show` route only: the admin's product page and the shop's partial product route fire the same event. Every part of the page is a block on the plugin's own `setono_sylius_gift_card.shop.product.show.*` events, registered in `prepend()` and listed in the README, so applications change the page through `sylius_ui` rather than by overriding it. Sylius' `sylius.shop.product.show.*` events do not fire there, and the theme's CSS for Sylius' product page applies because the page keeps its two column grid. `_gift_card_information.html.twig`, on Sylius' `sylius.shop.product.show.add_to_cart_form`, only renders where Sylius' own add to cart form is rendered for a gift card product, and is made of the same block templates. The preview script works within `#setono-gift-card-information`, which the page puts around both columns.

Only doctrine/orm is supported. Resources: `gift_card`, `gift_card_design` (translatable, images with front|back types), `gift_card_transaction` (append-only balance ledger, written only by the balance operator).

Code in `src/` stays **database agnostic**: applications run whatever database they choose, so no vendor error codes, vendor SQL or checks for a particular server. Database conditions are expressed through Doctrine's portable API (`LockMode`, and DBAL's exception classes such as `DeadlockException` or `UniqueConstraintViolationException`), and what those do not map is left alone. Tests may rely on the test application's MySQL.

A fixture (`AbstractResourceFixture`) hands each entry to its example factory as it is, so every option its tree declares has the same snake_case name in the example factory (`delivery_type`, `delivery_types`). The factory's normalizers turn what a YAML file can hold into domain types (enum cases with `::from()`, entities by code) and accept those types as they are. Random entries come from the fixture's `prototype`, which skips the tree, so the factory never relies on the tree having checked a value.

### Domain rules

- `GiftCard.amount`/`initialAmount` are integers in minor units (Sylius money convention). `initialAmount` is set explicitly — no implicit seeding.
- A disabled, "pending" GiftCard is created at add-to-cart (one per OrderItemUnit) carrying amount/message/design/deliveryType; a reconciliation pass at checkout complete creates cards for quantity-bumped units, removes stale ones, and sets each card's amount to its line's unit price (the amount the customer chose, never the unit total with its adjustments). Cards are enabled on payment and emailed (all delivery types); disabled on order cancel and on a full refund of the order (`sylius_order_payment.refund`) — a partial refund leaves them alone, since it does not say which items it covers.
- `deliveryType` (virtual|physical) is derived from `variant->isShippingRequired()` — never from product structure assumptions. A gift card product with a single delivery type gets no delivery option from `GiftCardProductFactory`, so Sylius treats it as a simple product and the shop shows no delivery choice for it.
- Balance mutations go through the balance operator exclusively, which writes `GiftCardTransaction` ledger rows (idempotency via nullable-unique `idempotencyKey`). A movement an admin makes by hand (an adjustment, or issuing a card in the admin) records who made it in `createdBy`: a copy of the signed in user's identifier, not a reference to the user, so an append-only ledger keeps naming them after the account is renamed or deleted. The controller or subscriber at the top reads it from the token storage and hands it to the operator, which never reads the security token itself. What the order and payment state machines record (redemption, restoration, issuing a bought card) names nobody, even when an admin's click set the transition off, and so do console commands and fixtures. The issuance of a bought card records the order that paid for it.
- The admin shows one status per card, `GiftCard::getStatus()` (`GiftCardStatus`): the first of pending, disabled, spent and expired that applies, else usable, which is exactly `isUsable()`. Pending is `isPending()` on an order that is not cancelled: the card of an order cancelled before payment is never issued, so `isPending()` stays true (it may be deleted, and goes with its unit), but its status is disabled, and `GiftCardPendingFilter`'s DQL leaves it out the same way. The grid column and the show page render it through one partial (`admin/gift_card/_status.html.twig`). Pending cards are hidden by the grid's `pending` filter (`GiftCardPendingFilter`, default value `''`), not by `createListQueryBuilder()`, which lists every card.
- Nothing below the top of a call flushes. The top is a controller, a console command (fixtures included), or a `kernel.request` subscriber that answers the request itself (`CheckoutGiftCardCoverageSubscriber`, which removes cards and redirects). Services, factories, operators and state machine callbacks only persist: whatever applies a transition flushes after it (Sylius' resource controller, Payum's storage after a capture or notify, the unpaid order canceller). Admin issuance is recorded on `pre_create`, so the resource controller writes the card and its ledger row in one flush. A factory that creates something shared persists it and remembers it until it is flushed (`GiftCardProductFactory`'s delivery option), since a repository lookup only sees flushed rows.
- Redeeming a gift card creates one Payment per card against the order, made with the offline gift card payment method (`redemption.payment_method_code`), leaving the order total intact. The method is a setup step (the button in the admin's setup warning, `CreateGiftCardPaymentMethodAction`; `setono:gift-card:create-payment-method`; the `setono_gift_card_payment_method` fixture; or by hand in the admin), never created on the fly: `GiftCardPaymentMethodProviderInterface` only finds it. While it is missing the shop refuses gift cards at the apply step, the checkout guard refuses to complete an order carrying any (`CheckoutGiftCardCoverageSubscriber` removes them), and the admin setup warning says so on every page. Balance is committed at order placement and restored, once per payment, when the gift card payment is refunded (`sylius_payment.refund`; cancelling the order refunds its gift card payments through `rollback()`, which restores nothing itself).
- An order the gift cards pay only in part stays `awaiting_payment` until the rest is paid, although its gift card payments are completed at placement (`GiftCardAwareOrderPaymentStateResolver` decorates `sylius.state_resolver.order_payment`). Sylius alone would call it `partially_paid`, which its shop never lets a customer pay (thank you page, account, a declined gateway payment) and its unpaid order expiry never cancels, so the card's balance would be held for good. Anything that resolves or asserts an order's payment state has to keep this. The gift card payments are added at placement after the customer's own payment, so the order's last payment is not the one for the rest: that is `setono_gift_card_remaining_payment()`, whose instructions the thank you page shows (Sylius' shows the last payment's).
- Gift cards cannot pay for gift-card line items (EligibleTotalCalculator default).
- The add-to-cart form is bound to the plugin's command, which cannot extend Sylius' `final` `AddToCartCommand`, so nothing Sylius maps on that class reaches it. Those constraints are mapped again on `AddToCartCommandInterface` (`AddToCartCommandInterface.xml`; today Sylius' `CartItemAvailability` stock check), where they also hold for an application's own command. When Sylius adds a constraint to its command (`CoreBundle/Resources/config/validation/AddToCartCommand.xml`), add it there too.
- A code is a bearer token, so every card issued from now on has a code of at least `minimum_code_length` significant characters (configuration; 12 by default, and `Configuration::MINIMUM_CODE_LENGTH` is the floor it cannot go below). `code_length` cannot be set below it, a code typed on the admin's create form is normalized and then held to it (`GiftCardCodeLength`), and so is a code given to the fixtures. Cards that already exist keep their code whatever its length (cards from 0.12 may have shorter ones), so `GiftCardCodeLength` skips persisted cards and redemption accepts any existing code.
- Promotions never discount a gift-card line (#116), so a card costs and holds exactly the chosen amount: `GiftCardExcludingFilter` keeps unit discounts off it, `GiftCardExcludingMinimumPriceDistributor` spreads order discounts over the other items only, and `OrderTrait` overrides `getPromotionSubjectTotal()`/`getNonDiscountedItemsTotal()` so order discounts and the "item total" rule leave gift cards out.
